# 04 — Derived Artifacts

Everything here is regenerated by `gamereg build` from `data/events.jsonl`.
Deleting all of it and rebuilding must lose nothing except hand-written prose in
game notes, which is preserved in place and never regenerated.

## Marker protocol

Generated regions are delimited by HTML comments, which are invisible in rendered
Markdown and survive every Markdown parser:

```markdown
<!-- gamereg:begin block=sessions -->
...generated...
<!-- gamereg:end block=sessions -->
```

Rules:

1. Build parses the note into an AST (`remark`), locates marker pairs by
   `block` name, and splices the subtree between them.
2. **Everything outside markers is emitted byte-identical to the input.** This is
   tested, not assumed.
3. A missing block is appended at the end of the file in canonical order.
4. An unpaired or nested marker is a hard error — abort the file, report it, do
   not guess.
5. Content inside a block is never read back. It is output only.

`Games.md` — one row per run, not per game, so replays appear separately.


Sorted by `ended_on` descending, open runs first. Imported runs are marked so
stated hours are never confused with measured ones.

## SQLite

`data/log.db`, gitignored, rebuilt from scratch every build. Never a source of
truth; deleting it costs nothing.

```sql
games(game_id, slug, title, release_year, developer, publisher, status)
game_platforms(game_id, platform)
game_genres(game_id, genre)
runs(run_id, game_id, platform, form, mode, started_on, ended_on, outcome,
     completion_criteria, rating, difficulty, minutes, hours_source, replay)
sessions(session_id, run_id, started_at, ended_at, minutes, logical_day, note)
breaks(break_id, session_id, started_at, ended_at, minutes)
aliases(game_id, alias)
events(event_id, ts, type, source, payload)   -- raw, for auditing
```

Views worth shipping, because they are what questions actually ask:

- `v_finished` — one row per finished run with everything flattened
- `v_by_year` — counts, hours and mean rating per year of completion
- `v_by_genre` — same, per genre
- `v_sessions_by_day` — for a calendar heatmap

This table is what makes "which RPG did I most recently like a lot?" answerable
with a real number instead of a guess.

## Determinism

`gamereg build` twice in a row must produce byte-identical output.

- No build timestamps anywhere in generated content
- Stable sort keys everywhere, ties broken by ULID
- Fixed decimal precision for hours (one place)
- LF endings, no trailing whitespace, single trailing newline
- Locale-independent formatting inside generated blocks — dates as ISO, numbers
  with `.` — because the file is data, not presentation

There is a golden-file test for this. It is the single most valuable test in the
suite.

## Site

Phase 3. Quartz over the vault, since it reads wikilinks and embeds natively.
`gamereg build --site` runs Quartz and writes `site/`. Publication is a GitHub
Action on push, or nothing at all — the vault is fully usable without it.

## Image ingestion

Every incoming file goes through the same pipeline before any event is written.
Deterministic, so re-ingesting the same photo is a no-op.

1. **Read EXIF**, then discard it (see below).
2. **Normalize**: auto-rotate from orientation, resize so the longest side is at
   most `images.max_edge` (default 2000px), encode to WebP at
   `images.quality` (default 82).
3. **Hash the normalized bytes** with SHA-256. That hash is the identity.
4. **Write** to `assets/<sha[0:2]>/<sha>.webp` if not already present.
5. **Append** the event carrying the attachment record.

A 4 MB phone photo lands at roughly 250–400 KB. That is what makes committing
images directly to git viable for a log meant to last decades — no LFS, no
external bucket, no broken links in five years. `images.keep_original: true`
stores the untouched file alongside for anyone who wants it, off by default.

### EXIF is read, then stripped

Two reasons, both mattering:

**`captured_at` is useful.** The EXIF timestamp says when the photo was actually
taken. Use it to populate `attachments[].captured_at`, and — when the command has
no explicit `--at` — to *suggest* a time. Suggest, never apply silently: a photo
sent the next morning would otherwise backdate the event.

**GPS must not survive.** Phone photos carry coordinates. This repository may be
published as a website. Stripping all EXIF on ingest is the default and is not
configurable to `false` for location tags specifically.

### Publication

`images.publish` (default `false`) controls whether attachments are copied into
the generated site. Covers follow `images.publish_covers`, separately, because
the licensing question differs: photos you took of your own shelf are yours; box
art fetched from a provider is not. See the open question in
[06-roadmap](06-roadmap.md).

When publication is off, the site renders a placeholder and the vault keeps
everything. The local record is never degraded to satisfy the public one.
